HOW I ADDRESSED YOUR TIER A CONCERNS

1. "Blocked dates don't equal booked dates"
   I never touch calendars. The tool uses a review velocity model: review count
   divided by assumed listing age gives reviews/month, divided by 0.6 review rate
   gives bookings/month, times 3.5 avg stay gives nights/month, capped at 85%
   occupancy. Every response includes a methodology field explaining exactly how
   the estimate was derived. No calendar inference, no availability gap guessing.
   (src/services/analysis.ts lines 170-255)

2. "Add confidence intervals to revenue estimates"
   Every estimate returns low (P25), mid (P50), and high (P75) ranges with a
   confidence level: high (50+ listings), medium (20-49), low (<20). Occupancy
   also carries its own confidence level. No single-number estimates anywhere.
   (src/services/analysis.ts lines 233-237)

3. "What happens when Apify fails mid-query?"
   Dual-scraper architecture: primary scraper fails, fallback scraper kicks in.
   Cache-first strategy: if data exists within 7 days, serve immediately (<2s).
   Every response includes dataFreshness ("live", "cached_48h", "cached_7d") and
   a cachedAt timestamp. If both scrapers fail, explicit error with both failure
   reasons — no silent garbage.
   (src/services/apify.ts lines 109-129, src/services/cache.ts)

4. "The 60-second timeout kills the response"
   Server timeout is 300 seconds. Apify actors also get 300 seconds each. But
   cached queries serve in under 2 seconds. The server auto-seeds Austin, TX
   cache on boot, so the most common first query hits cache immediately.
   (src/server.ts line 244)

5. "Add confidence intervals" (your suggestion)
   Done from day one. "Estimated $35K-$65K annual revenue (high confidence)" is
   the default output format. The methodology string documents every assumption
   so investors can judge the estimate quality themselves.
